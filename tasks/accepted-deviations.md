## 台账

### AD-001 不能自动接力，只能产出草稿

- **偏差**：原始设计稿 §1 要求「会话写入不可降级」，本库做不到。
- **为什么接受**：宿主的 `--resume` 对运行中会话会产生副本分叉；跨会话消息通道强制标注来源，无法无痕。见 `docs/adr/0001-config-only.md` §代价·3。
- **复核条件**：宿主提供对运行中会话的、可控制来源标注的稳定注入接口。
- **复核日期**：2026-10-29（下次复核：出现上述能力时）

### AD-002 四态判定没有运行时强制力

- **偏差**：主线程可以自称 `PRODUCING` 绕过判定，因为判定靠约定而非代码。
- **为什么接受**：纯配置库形态的固有代价。缓解措施：`scripts/scan-sessions.mjs` 独立从 transcript 计算，主线程写 `state.json` 时必须附脚本输出摘要。
- **复核条件**：误判导致实际损失，或用户要求升级为运行时形态。
- **复核日期**：2026-10-29

### AD-003 心跳是事后重建，不是实时上报

- **偏差**：规格 §5.2 要求「心跳间隔 >3 分钟 → FAILED」，实时监控。本库只能在下一轮读取时发现。
- **为什么接受**：无常驻进程。且实测固定 180s 会误判 63.1% 的会话（1275/2021），已改为会话自适应 p95（`docs/spec/state-model.md` §4.2）。
- **复核条件**：宿主提供实时 hook 或 `claude agents --json` 的频率足以支撑准实时轮询。
- **复核日期**：2026-10-29

### AD-004 token 预算只能估算

- **偏差**：状态行的 `budget` 是代理指标（调用次数 × 平均开销），不是真实用量。
- **为什么接受**：**前台交互会话**的 token 消耗在派发时不可知，中途不可查，只能用代理指标并标 `est:`。
  后台作业例外：`~/.claude/jobs/<id>/state.json` 有真实 `tokens`（实测 3,475,667 量级），能关联 job 的会话必须显示真实值。
- **复核条件**：宿主暴露子 Agent 的实时 token 用量。
- **复核日期**：2026-10-29

### AD-005 Stop hook 本质上验不了「活儿做完了没有」

- **偏差**：产品主张是「用户一次给到需求便一次做完」。Stop hook 看起来像在保证这件事，
  但它验的是**「本轮最后那句话宣称的检查，transcript 里做没做」**，不是「需求有没有被做完」。
  实测（2026-11-24，412 条判定记录）：真实项目、真实会话上的真实拦截 **0 次**。
- **为什么接受**：要判「做没做完」需要三样东西，**一样都不在 transcript 里**：
  1. 需求清单 —— 用户给的是自然语言，AI 自己拆的解构本身可能就是错的；
  2. 「N 个 bug」具体是哪 N 个 —— 「三个 bug 都修好了」这句话里没有它们的身份；
  3. 「做一半」与「做完了」的边界 —— 那需要读语义与业务意图，超出「断言 vs 证据」的判据范围
     （同 `README.md`「不能做」表里「判断『改得对不对』」那一条）。
  **硬做一个「完成度分数」会得到比 0 个拦截更坏的东西**：一个看起来在判、实际上是
  在数工具调用次数的数。那正是本仓最反复犯的错（`DF-056` 的 355 条里「拦住过 2 条」就是这么来的）。
- **代价**：用户不能指望这道闸告诉他「AI 是不是真做完了」。他能得到的是：**AI 说「我验证过了」
  的时候，这句话有没有依据**。这确实小于产品主张。缓解措施不是加强这道闸，而是把这个区分
  写进 README「边界二」/ ADR-0005 / CAPABILITIES §3 三处，让用户不会读错。
- **为什么不修**：不是「这一轮没空」，是**判据不存在**。修它的前提是宿主提供结构化的需求清单
  与结构化的完成事件，两者目前都没有。
- **复核条件**：宿主为「任务」提供结构化对象（有 id、有验收条件字段），且这些字段落进 transcript。
- **复核日期**：2026-11-24（下次复核：出现上述能力时）

### AD-006 `UNKNOWN` / `UNCHECKABLE` 一律放行，因此对「诚实地停下」零杠杆

- **偏差**：`detectClaims()` 认的是**完成性断言**。一个诚实地停下来说「还没做完，等你定方向」
  的回合没有这类断言，走 `no-checkable-claim` 直接放行。而用户经历的痛**恰恰是后者**
  （三轮问「还有哪些没做完」，代码零改动）。
- **为什么接受**：两件事叠在一起：
  1. `UNKNOWN` / `UNCHECKABLE` 放行是**有意的**（「没读到不等于没做」）。改成拦，
     会把「窗口截断」「丢后台没拿到退出码」「这句话没有证据源」全部变成拦，
     误拦率会直接毁掉这道闸（用户会把 hook 关掉，然后连记账都没有了）。
  2. 「认出诚实地停下」需要判「这个回合是在工作还是在汇报/等待」，而**在线时判不了** ——
     要判得看下一句，下一句还没发生。本仓已实测过同一类问题：`classify-stop.mjs` 的
     在线判定 95.4% → 100% `UNCLASSIFIABLE`（见 `README.md`「已知局限」）。
- **代价**：实测 `no-checkable-claim` 占**能解析记录的 77.8%**（154/198）。也就是说这道闸
  对**绝大多数**收工回合没有触发条件。这个数字本身就是「本方向没有杠杆」的证据，
  不是「已经很安全」的证据。**必须这样读，README「边界二」已明写。**
- **为什么不修**：改放行策略 = 换一个产品（会拦诚实的人）；认「诚实停下」= 需要未来信息。
  两个都不是这一轮能修的。
- **复核条件**：宿主在 `Stop` 事件里提供结构化「本轮意图」（如 `end_turn_reason`），
  或在 `transcript` 里落盘类似信号。
- **复核日期**：2026-11-24（下次复核：出现上述信号时）

### AD-007 断言里的**数量**从不与实测比对：「1626/1626 通过」只要跑过任意一次测试就算有证据

- **偏差**：`test-count` 族（「全部测试通过，1626/1626」）只判「本会话跑过一次测试运行且没报错」，
  **不核对数字**。实测确认：声称 `1626/1626` + 实际只跑出 `ℹ tests 3` → `allow, all-claims-supported`；
  声称 `1626/1626` + 实际 `ℹ tests 0`（空目录）→ `allow`。
- **为什么接受**：
  1. 测试运行器的输出格式**因项目而异**（`node --test` 的 `ℹ tests N`、pytest 的 `N passed`、
     jest 的 `Tests: N passed`、mvn 的 `Tests run: N`、gradle 的 `N tests completed`……）。
     可靠地抽出「实跑了几条」需要每种格式一条解析规则，而**解析失败的方向是假阳性拦截**
     —— 那比漏报更贵（见「误拦的代价不对称」，README「关键设计二」）。
  2. 数字对不上≠撒谎。同一个会话里可能跑了多个测试文件、多次运行、或在子 agent 里跑，
     取哪一个输出和哪个数字比，本身就是个可争议的选择。
  3. **本轮已经收紧了同一族的一个更明确的洞**（DF-058：空输出不算验证）。
     数量比对是另一个量级的工程（要多格式解析器 + 误报调参），不是顺手能做的。
- **代价**：一个会话可以只跑 3 条测试，然后说「1626 条全过」，闸门放行。
  实测确认这条路径今天是开的。**它不是理论风险。**
- **为什么不修**：格式覆盖不全时，修法本身会**制造**假阳性拦截 —— 用「拦错」换「少漏」，
  在一个 fail-open 设计的闸上不划算。要做就应该做成「比对得上就加分、对不上只警告不拦」，
  而那是新功能，不是本轮的修复。
- **复核条件**：出现一条能可靠识别 ≥3 种主流测试运行器计数的解析规则（且在本机语料上
  假阳性率 < 5%），或宿主开始落盘结构化的测试结果。
- **复核日期**：2026-11-24

## 复核流程

每轮 run 开始前，主线程扫一遍本文件：

1. 复核条件已满足的 → 移入 `dev-findings.md` 并标 `triaged`
2. 复核条件仍不满足的 → 更新复核日期
3. 条目描述的偏差已消失的 → 删除，并在 CHANGELOG 记录
