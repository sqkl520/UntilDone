# 派发契约

> 每个子 Agent 的 prompt = **本文件的公共段** + **Planning 现写的域专属段** + **baseline 事实快照**。
> 三段缺一视为规划缺陷，退回 Planning Agent（规格 §2.8）。

## 1. 拼装规则

```
prompt = templates/dispatch.md（公共段，长期稳定）
       + planning 现写（域专属：目标 / 文件清单 / 风险假设 / 定制检查项）
       + templates/baseline.md（当轮事实快照：commit、规模、已知问题数）
```

**为什么域专属段不预置**：参考项目预置了 30+ 份 `review-plan.md`，结果全部腐烂——没人知道哪份是当前真相。域段必须每次现写，写完即用完。

**为什么 baseline 必须共享**：所有 Agent 对同一组数字发言，才能发现「A 说 87 个文件、B 说 92 个」这类矛盾。baseline 由主线程派发前生成，不读其他 Agent 的输出。

## 2. 每个 Agent 必须收到的四样东西

| # | 内容 | 缺失后果 |
|---|---|---|
| 1 | 原始任务描述（不是别人的转述） | Agent 会优化一个错误的目标 |
| 2 | **预先声明的验收标准** | 事后编造标准，验收失去意义 |
| 3 | 产出形态声明（`artifact` / `exploration` / `hybrid`） | 无法判定「8 分钟无 Write 是否异常」 |
| 4 | token 预算与容忍窗口 | 无法做预算管理，只能事后惊讶 |

## 3. 独立性约束（防锚定）

| 角色 | 不得读取 | 原因 |
|---|---|---|
| 锐评 Agent | 执行 Agent 的自我评价、执行日志 | 会在别人的框架里打分 |
| 验收 Agent | 锐评 Agent 的分数 | 锐评管「好不好」，验收管「过不过」，混了就变成一个人 |
| 批判 Agent | 其他批判 Agent 的结论 | 防止第一个发言者定义议题 |
| 红队 Agent | 执行 Agent 的薄弱点自述 | 会直接照着打，失去独立构造反例的意义 |
| 探针 Agent | 目标 Agent 的推理文本，**只读工具调用日志** | 推理文本会诱导探针认同目标 |

**实现方式**：不靠 prompt 里写「请不要读」，靠**不提供路径**。主线程派发时只给必要的输入文件路径。

## 4. 角色清册

| 角色 | 工具白名单 | model | 职责 | 不可合并的理由 |
|---|---|---|---|---|
| `planner` | Read, Write, Glob, Grep | inherit | 拆解任务，声明验收标准与产出形态 | — |
| `executor` | Read, Write, Edit, Bash, Glob, Grep | inherit | 实质执行 | — |
| `research` | Read, Grep, Glob, WebSearch, WebFetch | inherit | 搜集外部事实 | 需要网络，executor 不该默认有 |
| `critic` | Read, Grep, Glob | inherit | 质疑**拆解与前提** | 输入是拆解图，不是交付物 |
| `redteam` | Read, Grep, Glob, Write | inherit | 攻击**交付物与结论** | 输入是交付物，不是拆解图 |
| `review` | Read, Grep, Glob, Write | inherit | 质量评分（1–10） | 主观评分，与客观判定分离 |
| `acceptor` | Read, Grep, Glob, Write | inherit | 对照预声明标准判定，一票否决 | 客观判定，不写分数 |
| `repair` | Read, Write, Edit, Bash, Glob, Grep | inherit | **仅**在可定位的局部修复路径上接手（§8.3 的 C1/C2/C3 全成立）；默认失败路径是盲重采样 | 需要写权限，但不得改验收标准，也不得扩大到 `outputs` 之外 |
| `probe` | Read, Grep, Glob | haiku | 只读日志判 `HEALTHY/UNFOCUSED/LOOPING` | 纯判定，允许短生命周期 |
| `relay` | Read, Grep, Glob, Write | inherit | 产出接力草稿 | — |
| `safety` | Read, Grep, Glob | haiku | 检查草稿是否触碰红线 | 输入是草稿，与 relay 的输入不同 |
| `resolution` | Read, Grep, Glob, Write | inherit | 裁决分歧 | 输入是双方原话，与 safety 不同 |
| `verifier` | Read, Grep, Glob, Bash, Write | inherit | 核**主线程自己**说过的可机械验证的事实（数字 / 路径 / 命令输出 / grep 与行号） | 输入是主线程的原文，与其他角色的输入**不重叠**；且它只核事实不核判断，与锐评（好不好）、验收（过不过）是三件事 |

**`critic` / `redteam` / `review` / `acceptor` / `safety` / `probe` 全部没有 `Edit`**。这不是 prompt 里的「请勿修改」，是工具集物理限制。`scripts/check-structure.mjs` 会验证这一点。

**`verifier` 是唯一的例外形态：`readonly: true` 且带 `Bash`。** 它必须跑只读命令才能核事实
（`grep` / `wc` / `node --test`），没有 `Bash` 它只能退化成「读一遍源码觉得它对」——那是判断，
不是核验。硬门的规则**没有放松**：带 `Bash` 的只读角色必须
① 在 frontmatter 写 `bashScope: read-only`，**且** ② 在正文给出 `## 允许的命令` 清单。
两条缺一条照样红。它同时必须是**叶子**（`tools` 无 `Task` / `Agent`），否则 §7 的
「深度恒 1」当场失效 —— `checkHubVerifier()` 专门核这一条。

**`verifier` 为什么不能与 `acceptor` 合并**：验收核的是**交付物**（预声明的 AC 逐条），
verifier 核的是**主线程的输出**（它这一轮说过的数字与路径）。两者的对象不同，
而「主线程说的话有没有证据」这件事，此前没有任何角色被派去做。

**为什么 `relay` 和 `safety` 不合并**：合并后就是「自己写草稿、自己审红线」，重演参考项目「锐评自己写自己」的失效模式。

## 5. 产出形态声明格式

Planning 派发每个 Agent 时必须写明：

```yaml
shape: artifact | exploration | hybrid
acceptance:                      # 预声明，事后不得增补
  - id: AC1
    criterion: <可观测事实>
    evidence: <引用形式，如 file:line>
    fail_if: <什么情况直接否决>
token_budget_pct: 40
timeout_min: 8
```

## 6. 返回值格式

子 Agent 的最终返回**不是散文**，是结构化四元组：

```
## 交付物
<路径 或 内联结论>

## 执行日志
<关键决策点，每条一行，不写过程叙事>

## 我认为的薄弱点
<1–3 条，主动暴露>

## 我产出的文件
- <路径> —— <字节数>      （或：无）
```

返回超过 18 行视为格式不可解析，按 `docs/spec/state-model.md` §2 判定。**注意：不得因「没有交付物」直接判失败**——必须先过状态判定，`EXPLORING` 态的空返回是正常的。也**不得**因「停了很久」判 `FAILED`：那个推断已删除（`state-model.md` §2.0.1），`FAILED` 只认宿主上报。

**四个字段名是主线程读返回时的键，少一个就读到一个不存在的东西**，所以它由
`scripts/check-structure.mjs` 的 `dispatchQuartet` 检查守着：整行比对
`docs/spec/dispatch-contract.md` / `templates/dispatch.md` / `oversight-executor.md` /
`oversight-repair.md` 里的字段标题，缺一个即红。

第四节 `我产出的文件` 与前三节的区别：前三节给人看，第四节**给机器对账**。
它的格式与纪律（只写真的写过的路径、字节数写不准就省略）见 `templates/dispatch.md`「我产出的文件」一节。

## 7. 递归派生

**v0 的实际深度是 1 层**（主线程 + 一层执行者）。这是**设计选择**，也是**当前配置的事实**。

### 为什么是 1 层：三条实测证据

1. **13 份角色定义的 `tools:` 白名单里，没有一个含派生子 Agent 的工具。**
   实测全集只有 8 种：`Bash / Edit / Glob / Grep / Read / WebFetch / WebSearch / Write`
   （`verifier` 用的是其中已有的 `Bash`，没有引入新工具名）。
   Claude Code 的 `tools` 语义是**精确白名单**（列出即只给这些），所以这 13 个角色
   **物理上派生不出下一层**。
2. **宿主对 subagent 本来就不开放这条能力**（只对 fork 形态例外）。
   即便给某个角色加上工具名，深度 2 的下一层仍然拿不到派生能力。
3. **结构硬门核这条了**（2026-11-23 起）。修前 `checkAgents()` 只校验「只读角色不得含
   `Edit`/`Bash`」，不校验派生工具的有无 —— 也就是说「我们以为自己有几层」这件事
   **没有任何检查守着**，只能靠人读角色定义。`checkDispatchDepth()` 现在取全部角色
   `tools` 的并集，有派生工具就要求文档改成「深度 ≥2」；`checkHubVerifier()` 另外
   指名核 `verifier` 必须是叶子。两条都不许靠人眼。

### 平台能力 ≠ 本仓架构（这条要单独说清）

宿主**支持**更深的派生（默认上限 3 层，见 `docs/adr/0001-config-only.md`）——
那是**平台能力**，不是本仓的架构承诺。榜样的区别：

| | 含义 | 本仓现状 |
|---|---|---|
| 平台能力 | 宿主允许做到几层 | 3 层 |
| 本仓架构 | 这一版**实际采用**几层，以及为什么 | **1 层** |

**把平台能力写成架构承诺，是本仓已经犯过一次的错**（`docs/design/2026-11-10-agent-framework-skeleton.md:159`
当时就判定「规范声称的能力在实际配置里不存在，这比没有规范更坏 —— 一个读者会据此设计三层方案」）。
本节的修改就是那次判定的执行。

### 递归不在 v0 范围内

若将来要做，前提是三条**同时**满足，缺一不可：

1. 给需要递归的角色**显式加**派生工具，并接受随之而来的 token 代价（约 15×）；
2. 每一层派发必须写明「**为什么需要这一层，而不是由父级自己完成**」——
   写不出理由就不许派生；
3. 它需要**独立裁决**，不随 v0 顺延（即：不能因为「v0 没做完」就默认下一版要做）。

**深度 ≥2 时**，报告中必须标注「此结论在深度 N 仍未收敛」。

## 8. 失败处理：盲重采样是默认，局部修复是例外

> 本节约束 **Hub（主线程）在派发失败之后做什么**。失败包括三类，判据都来自外部：
> 验收判不通过（`oversight-acceptor` 的预声明标准）、红队阻断（`oversight-redteam` 的
> 关键路径结论）、执行失败（宿主上报的 `FAILED`，见 `state-model.md` §2 第 0 行）。

### 8.0 为什么默认不是「交给 repair 去修」

外部实证（1.5B / 3B / 7B，匹配预算，小模型代码生成）：

| 观察 | 数字 |
|---|---|
| 盲重采样（丢弃失败输出，从**原始任务契约**重新采样）在 7B 以下是最强条件 | 7B 才与最佳「修复」条件持平 |
| 盲重采样相对「修复」的 token 消耗 | 少 **2.5–5.5 倍** |
| 把失败程序喂回模型后，重试产出与上次近似相同的程序 | **33–68%**（锚定效应） |
| 盲重采样的重复率 | **2–14%** |
| 「执行反馈」在一条「无内容的失败通知」之外的额外信息贡献 | **无可测量的额外贡献** |

结论只有一条与本节有关：**失败输出本身是锚定源，不是信息源。**
所以「失败 → 把失败上下文交给 repair」这个默认动作，是在主动制造重复。

> **证据等级**：这是**外部研究**的结论，不是本仓实测（本仓没有做这个对照实验）。
> 它支撑的是「默认值」这个选择，不支撑「本仓的失败率会下降几个点」这类断言。
> 本仓自己的失败样本量在任何时候都不足以做这个对照 —— 谁能给出本仓的对照数据，
> 谁才可以按 §8.5 打开自修复。

### 8.1 两条路径的判据（逐项对照，不取交集）

| 项 | **A. 盲重采样（默认）** | **B. 局部修复（例外）** |
|---|---|---|
| 准入 | 无条件。**任何**一次失败先走这条 | 必须**同时**满足 §8.3 的 C1 / C2 / C3 |
| 输入 | 原始任务契约（`task-graph.json` 该子树的 `goal` / `acceptance[]` / `shape` / `outputs`）+ **无内容失败通知** | 原始任务契约 + **定位结论**（`file:line` 集合） |
| 明确**不**给 | 失败输出、验收理由正文、红队反例正文、失败实例的「执行日志」与「我认为的薄弱点」 | 失败实例的「执行日志」与「我认为的薄弱点」（定位结论替代它们） |
| 执行者 | **新的** Spoke 实例（新 nonce；`oversight-executor`，或同一角色的新实例） | **新的** Spoke 实例（`oversight-repair`，或 `oversight-executor`） |
| 失败实例的下场 | 其输出**整份丢弃**，不进入下一轮的上下文 | 同左。**不得**让原失败实例对着自己的输出打补丁 |
| 验收标准 | 与首轮**逐条相同** | 与首轮**逐条相同** |
| 判定「过不过」的人 | Hub 读 `oversight-acceptor` 的结论 + 预声明的 `acceptance[]`（外部 oracle） | 同左 |
| 谁来判定「能走 B」 | **Hub**（§8.4） | 同左 |

**两条路径的输入差就是全部差异**：A 只多一句「上一次派发失败」，B 多一组 `file:line`。
两者都**不含**失败输出。区别在于 B 把「修哪里」也变成了外部给定的事实，A 不给。

### 8.2 A 路径（盲重采样）的动作

1. 记录失败事实：在 run 目录记一行「子树 `<id>` 第 N 次派发失败」（原因类别即可，不记正文）。
   原因类别只有三个合法值：`acceptance` / `redteam` / `execution`。
2. **丢弃**失败实例的全部输出：不把它的交付物路径作为新实例的输入，不引用它的返回文本。
3. 从 `task-graph.json` 重新拼一次提示词（`node scripts/compose-agent-prompt.mjs compose …`），
   `--stop` 与 `--constraint` 与首轮相同；**不得**新增「上次漏了 X」之类的定向约束。
4. 新 nonce（`compose` 默认就会生成；不要手写，也不要沿用失败实例的 nonce）。
5. 新实例返回后，按 Phase D 对账、Phase E 验收，与首轮流程完全相同。

**给新实例的「无内容失败通知」只有这一种合法形态**（可机械判，判据见 §8.6）：

```
上一次派发失败（原因类别：acceptance / redteam / execution 之一）。本次从原始任务契约重新开始。
```

**不合法**的形态举例（不是风格问题，是锚定源）：

- 附上验收逐项判定表、`fail_if` 触发点、红队的反例列表；
- 附上失败交付物的 `file:line` 片段；
- 用 `--prior-failure` 传一段「上次你在 X 处漏了 Y」的描述 —— 那是缩小范围 + 定向锚定。

### 8.3 B 路径（局部修复）的准入：三条同时成立

| 代号 | 条件 | 判据（谁核、怎么核） |
|---|---|---|
| **C1** 定位 | 失败原因能落到**至少一个** `file:line` | Hub 写出 `{file, line}`；`file` 必须是**当前磁盘上存在**的文件（Hub 自己 `stat` 一次），`line` ≤ 该文件行数。写不出 `file:line` 的条件不满足 |
| **C2** 局部 | 上述位置**全部**落在该子树的 `outputs` 内，且失败点集合被这些位置**全覆盖** | 机械：`locators.map(file) ⊆ outputs`（路径归一化后比较）；且每个失败原因至少对应一个 locator。有任何失败原因没有 locator → 不满足 |
| **C3** 不复用 | 接手的是**新实例** | 机械：新 nonce ≠ 失败实例的 nonce。同一 nonce 再派一次 = 原实例继续干活，禁止 |

**C2 为什么要求位置在 `outputs` 内**：不在产出清单里的文件不是这次任务的产物。
在别人的产物上打补丁不是局部修复，是越界修改（`templates/dispatch.md` 纪律 5），
此时正确动作是 A 路径重派，或者退回 planner 重拆。

**C2 为什么要求「全覆盖」**：只定位了 3 个失败点中的 1 个时，「局部修复」会把另外 2 个
留给下一轮验收 —— 那不是修复，是分批失败。分批失败的成本比一次盲重采样高。

### 8.4 「可定位性」由谁判

**由 Hub 判。** Hub 是协调者，它手里有失败结论、任务图和磁盘，判这一步不需要它读懂代码语义。

**不许**由失败的 Spoke 自报「我能修」。可判定的形式：

| 情形 | 判定 |
|---|---|
| 准入记录里出现「失败实例自述可修复」作为唯一依据 | **违规**，按 A 路径重派 |
| Hub 写出的 C1 定位在磁盘上不存在，或行号越界 | 条件不满足，按 A 路径重派 |
| Hub 写出的定位文件不在 `outputs` 内 | 条件不满足，按 A 路径重派 |
| 定位结论里含失败交付物的代码片段 | 仍可走 B，但片段**不得**进入新实例的提示词（只给 `file:line`） |

**Hub 判错的代价是不对称的**：误判「可定位」会让修复对着错误的位置改（A 路径的一次重采样成本）；
误判「不可定位」只是多花一次重采样。所以判不准时选 A —— **默认值本身就是这个不对称的表达**。

**为什么不设「Debugger」这个独立角色**：本版的实际派生深度是 1 层（§7），没有余量再挂一个
只做诊断的岗位；「独立诊断」由 Hub 自己完成（它跑只读命令定位即可），「修复」由新实例完成。
两件事仍然分开，只是分开在两个执行者上，而不是两个角色定义上。

### 8.5 轮次、熔断，以及「7B 以上」的例外

| 规则 | 判据 |
|---|---|
| 同一子树最多派发 **3** 次（含首轮） | 数该子树在 run 目录里的派发记录（nonce 计数） |
| **盲重采样最多 2 次** | 第 2 次盲重采样仍失败 → 第 3 次**不得**再走 A |
| 第 3 次必须换策略 | 换 B（此时 C1 若仍不成立，见下一行）／换拆解（退回 planner）／交人 |
| 同一子树第 3 次仍失败 | 提交失败报告，**不假装通过**（与 Phase E 原有规则一致） |

**7B 以上的自修复例外**：允许保留「把失败输出喂回同一实例」的做法，但**不得默认开启**，
且必须同时满足三条：

1. 用的是 7B 以上的模型（写清模型标识与参数，不写「大模型」）；
2. 有**本仓**的对照数据：同一批失败任务上，自修复的成功率高于盲重采样，
   且 token 消耗差距不超过 2 倍（对照方法与样本量写进 `docs/research/` 并登记索引状态）；
3. 该结论经 ADR 裁决，ADR 里写明「反悔信号」。

**第 2 条目前无法机械判定** —— 它要求一份不存在的实验，而「不存在」无法被脚本核。
所以本版的实际状态是：**这条路径不可开启**（`compose-agent-prompt.mjs` 没有任何参数能
把失败输出送进新提示词；`templates/dispatch.md` 的输入清单里也没有它）。
将来要开，必须先有那条 ADR，再改代码，并在 `docs/CHANGELOG.md` 里记一笔。

### 8.6 哪些是机械可判的，哪些不是

| 规则 | 能不能机械判 | 判据形态 |
|---|---|---|
| 新实例的 nonce 与失败实例不同 | **能** | 比两行 `declare` / `compose` 记录的 nonce |
| 两次派发的验收标准逐条相同 | **能** | 比 `task-graph.json` 的 `acceptance[]` 序列化结果 |
| 定位文件存在且行号不越界 | **能** | Hub 侧 `stat` + 读行数 |
| 定位位置 ⊆ 子树的 `outputs` | **能** | 路径归一化后取子集 |
| 失败通知是「无内容」形态 | **能（弱）** | 只认上表那一个固定句式；自由文本一律按「有内容」处理，拒绝注入（§8.2） |
| 「失败原因可定位到局部」这件事本身 | **不能** | 它依赖人／Hub 对代码结构的判断。本节能做的是把「判错」的成本压到一次重采样，而不是把判断变成脚本 |
| 7B 以上自修复优于盲重采样 | **不能** | 见 §8.5 |

最后两行不是漏洞，是**如实列出**。把它们写成「应该」「原则上」才是漏洞。

### 8.7 与其它规格的关系

- **硬约束 2 的「修复角色」仍然存在**：`oversight-repair` 是 B 路径的执行者，不是默认路径的执行者。
- **`original-design.md` §5.5 的「带诊断重跑」被本节收紧**：那份设计允许在 prompt 里带
  「上次失败模式」；本节把它限定为**无内容通知**（A 路径），或**外部给定的 `file:line`**（B 路径）。
  历史存档不改，冲突时以本节为准（`original-design.md` 文件头已声明这一点）。
- **`state-model.md` §2 的处置列不变**：`FAILED` 仍是「重跑」，但重跑现在默认是盲重采样。
